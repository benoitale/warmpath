# AGENTS.md

## Project

WarmPath is a static, single-page web app that maps warm introduction paths from a company's investors, board, and leadership team into its target enterprise accounts.

It is a demo artifact. It runs entirely on public data, has no backend, no database, no authentication, and no runtime API calls. All data is a JSON file committed to the repo and imported at build time.

Stack: Vite + React 18 + TypeScript (strict) + Tailwind CSS. Vitest for tests. Node 20. Package manager: npm.

## Setup commands

- Install: `npm install`
- Dev server: `npm run dev`
- Tests: `npm test`
- Typecheck: `npm run typecheck`
- Lint: `npm run lint`
- Validate the graph data: `npm run validate:graph`
- Build: `npm run build` (runs validate:graph first, then vite build)

## Hard rules

These are not style preferences. Violating them breaks the demo.

Every edge in the graph must carry a real `source_url` and a `source_accessed` date. Never invent, infer, or guess a relationship. If you cannot find a public URL that states it, do not add the edge. `npm run validate:graph` fails the build on any edge missing a source, and that check must never be weakened or skipped.

Public, company-level data only. Fund portfolio pages, company websites, press releases, published executive bios. Do not scrape LinkedIn. Do not collect or store personal contact details (email addresses, phone numbers, home locations) for anyone. Person records hold name, public role, and public employment history only.

No network calls at runtime. Collectors run offline as build scripts and write to `data/graph.json`. The app itself must load and render with the network disabled.

No backend, no database, no auth, no environment secrets. If a task seems to need one, stop and leave a comment rather than adding it.

Respect file ownership. Each session brief lists the files it owns and the files it must not touch. Sessions run in parallel. Editing outside your scope causes merge conflicts and wastes everyone's time.

## Code style

- TypeScript strict mode. No `any`. No non-null assertions without a comment.
- Functional React components, named exports only, PascalCase filenames for components.
- Scoring and data-transform logic is pure: no I/O, no dates read from the system clock (pass `now` in as a parameter so tests are deterministic).
- Tailwind utility classes only. No CSS modules, no styled-components.
- Conventional commit format (`feat:`, `fix:`, `chore:`, `test:`).

## Testing

- Vitest. Every pure function in `src/scoring/` and `src/drafts/` needs unit tests.
- Tests run against `data/graph.fixture.json`, never against `data/graph.json`. The fixture is small, hand-checked, and stable. Do not edit the fixture to make a failing test pass.
- Collectors need tests against saved HTML fixtures in `scripts/collect/__fixtures__/`, not against the live web.
- Aim for meaningful coverage of scoring edge cases, not a coverage percentage.

## Project structure

```
data/
  graph.json            generated by collectors, committed
  graph.fixture.json    small hand-checked fixture for tests
scripts/
  collect/              per-source collectors (session 01)
  validate-graph.ts     schema + source-url validator (session 00)
src/
  schema/               zod schema and TS types (session 00)
  scoring/              path finding and scoring (session 02)
  drafts/               intro draft generation (session 05)
  components/
    search/             account search and ranked results (session 03)
    path/               path detail cards (session 03)
    graph/              graph visualization (session 04)
  App.tsx               shell and routing (session 03)
```

## Development workflow

- Branch from main. Branch names: `session-NN-short-name`.
- One PR per session. Do not merge your own PR.
- The PR description must list: what you built, what you deliberately did not build, and any edge you dropped for lack of a source.
- Run `npm run typecheck && npm test && npm run validate:graph` before opening the PR.

## What to avoid

- Do not add dependencies beyond what the brief names. If you think one is needed, say so in the PR description instead of installing it.
- Do not build a login, a settings page, an export feature, or a dark mode toggle.
- Do not make the graph visualization the landing view. It is a secondary tab.
- Do not write copy that sells the product. Interface copy names what things do.
